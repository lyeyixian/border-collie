# stricli for the CLI layer (commander considered and rejected)

The CLI layer moves from hand-rolled `node:util` `parseArgs` to `@stricli/core` — the project's first runtime dependency, taken deliberately. The pain is boilerplate in `src/cli.ts` (manual integer coercion, subcommand routing, a hand-maintained USAGE string that can drift from the real options) plus room to grow per-command flags without the single flat option set hurting. Commander was the other finalist; both are zero-transitive-dep and equally maintained, so footprint and health didn't separate them (full comparison with sources: `docs/research/commander-vs-stricli.md`). The deciding factor: **in a repo maintained by autonomous agents, a strongly typed API is a better guardrail than training-data familiarity.** stricli checks the flag spec against a declared `Flags` type; commander's `opts()` returns `Record<string, any>`, so an agent's familiar-but-wrong commander code passes typecheck silently, while its unfamiliar-but-wrong stricli code fails the build and gets iterated on. stricli's execution contract also matches the codebase's existing style — `run(app, args, context)` takes an injected context and returns an exit code without ever calling `process.exit`, the same DI + exit-code pattern `cli.ts` already uses by hand.

Consequences: the zero-dependency state ends (one package, no transitive deps); the spec needs `caseStyle: "allow-kebab-for-camel"` to keep the `--max-workers`-style flag spellings; the `/^\d+$/` integer validation survives as a custom parse function (stricli's `numberParser` accepts floats); the code splits into spec and impl files rather than staying in one `cli.ts`; generated help replaces the USAGE options block, killing the drift risk. Commander's counterweight — vastly larger training-data presence — was real but argues equally for the status quo, and the typecheck gate neutralizes it.
