# Vendor the Worker's skills into the target repository instead of installing them at run time

`border-collie init` writes the skills a Worker session invokes into the target repository under `.claude/skills`, byte-identical to their upstream source, along with the agent docs those skills read (`docs/agents/issue-tracker.md`, `docs/agents/triage-labels.md`). The Worker workflow no longer adds a plugin marketplace or installs a plugin, and a template guard fails if either comes back.

The Worker job used to run `claude plugin marketplace add mattpocock/skills` followed by `claude plugin install mattpocock-skills@mattpocock`, resolving both against upstream at the moment the job started. That is a floating install on an unattended fleet — exactly what the pinned `npm install -g border-collie@<version>` two steps above it exists to prevent. The Tick's cron fires every half hour with nobody watching, so an upstream change lands in a sleeping fleet overnight, and the failure it produces is not a failed job: the Worker prompt invokes its skill by name with no fallback, so a session that cannot resolve the name receives unhandled text and improvises. That surfaces as an oddly-shaped pull request, which costs an Attempt and a human read to diagnose.

**The whole closure is vendored, not just the skill the prompt names.** `implement` reaches `/tdd` and `/code-review`; `/tdd` reaches `/codebase-design`; three of those carry support files they link to. A skill vendored without what it invokes fails the same way the missing skill did, one level deeper in. `SKILL_FILES` (`src/core/scaffold.ts`) is the list, and guards in `tests/adapters/scaffold.test.ts` read the vendored files' own text: every relative Markdown link must resolve to another vendored file, and every `docs/agents/*.md` path named in prose must be a file the scaffold writes.

**Byte-identical, because repository ownership only means something if what it received was the real thing.** A copy patched on the way out is a fork somebody maintains against a moving upstream, and it makes the next re-vendoring a merge instead of a copy. Nothing is rewritten: `scaffoldContent` routes the CLI pin rewrite to the two workflows and hands everything else over untouched. The source is `mattpocock/skills` at plugin version 1.2.1 — `skills/engineering/{implement,tdd,code-review,codebase-design}`, minus each skill's `agents/openai.yaml`, which is Codex packaging that Claude Code never reads.

**The tracker doc and the triage-label map are vendored too, and they are not upstream copies.** `code-review` fetches the originating ticket through `docs/agents/issue-tracker.md` and tells the agent to run `/setup-matt-pocock-skills` when it is missing — an interactive session, and a dead end inside a headless Worker job. A freshly onboarded repository has neither the doc nor that skill, so `init` writes the doc directly and the interactive skill is deliberately left out of the closure: nothing ever reaches for it. The triage-label map rides along because every onboarded repository needs it now that border-collie's own two labels carry a `border-collie:` namespace (issue #156) — it is the one place that says which label strings are the repository's to rename and which two are not.

**After `init` writes them, the repository owns them.** An existing file is left alone on a re-run and reported as skipped, overwritten only with `--force` — the same treatment the workflows have always had. The operator may edit a vendored skill, add their own, or delete one. Exactly one name is load-bearing: `WORKER_SKILL` (`src/core/types.ts`), which `workerPrompt` types into the prompt and off which the vendored path is keyed, so the two ends cannot be renamed apart.

## Considered Options

- **Keep the run-time marketplace install, but pin the plugin version** — rejected: it narrows the window without closing it. The install still needs network and an upstream that is up, on every Worker job of every Tick, and the target repository still cannot edit what it runs. Vendoring costs the same disk either way and removes the dependency entirely.
- **Ship border-collie's own `implement` skill rather than vendoring somebody else's** — rejected: it is a fork with extra steps. The upstream skill is maintained, and the value of `init` here is delivery, not authorship. ADR 0007 rejected authoring a conflict skill for a different reason — one caller, no sharing — which does not apply to a skill the target repository is meant to read and edit.
- **Vendor the interactive `setup-matt-pocock-skills` skill along with the rest of the closure** — rejected: its only job is to produce the two agent docs, interactively, in a session that has a human in it. Writing the docs directly is the same outcome without the dead end, and it keeps eight files out of every scaffolded repository.
- **Fetch the skills at `init` time from the marketplace rather than shipping them in the tarball** — rejected: it moves the floating install from the Worker job to `init`, which is better but still means two scaffolds of the same CLI version can disagree. Shipping them alongside `dist` makes a version of border-collie a single fixed thing, and the smoke test proves the tarball actually carries them.
- **Extend the guard to fail on any `claude` subcommand in a workflow** — not taken: the Worker job legitimately installs and runs Claude Code. The guard names the plugin system specifically, and ignores comment lines so a template can explain in prose why it no longer installs anything.

## Known Limitations

- **A scaffolded repository's skills go stale, and nothing tells it so.** This is the trade vendoring makes: the repository stops tracking upstream the moment `init` writes the files. `border-collie init --force` re-vendors whatever the running CLI ships, which is the same lever the CLI pin uses, and it overwrites local edits — so a repository that has edited a vendored skill has to merge by hand. There is no drift report.
- **Byte-identity is established when the files are vendored, and cannot be re-checked in the repository.** No test can reach upstream, so the guards here check the closure's internal consistency, not its fidelity. The upstream source and version are recorded above; verifying them means diffing against `mattpocock/skills` by hand. What *is* checked is that `init` does not alter them on the way out: `tests/cli/context.test.ts` compares a scaffolded vendored file against this repo's own byte for byte, with none of the pin normalisation a workflow gets.
- **The closure is derived by reading the skills, not by resolving them.** Three guards read the vendored text — relative Markdown links, `docs/agents/*.md` references, and slash-command invocations outside fenced code blocks — so a re-vendored skill that reaches somewhere new fails the suite rather than a Worker job. What they cannot do is confirm a name is a *skill*: the reader excludes fenced code, which is where every false positive in the current corpus lives, but a URL path or a placeholder written in prose would be reported as an unvendored skill, and the fix is a judgement call each time. Nothing checks the reverse direction either — a skill invoked only from inside a code fence would be missed.
