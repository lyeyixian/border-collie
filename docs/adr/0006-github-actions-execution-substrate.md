# GitHub Actions as the execution substrate for the Orchestrator and Workers

The Orchestrator runs as a single Tick per GitHub Actions job in the target repository, and each Worker runs as its own Actions job, dispatched by `workflow_dispatch` with the Ticket and Attempt number as explicit inputs. The resident run loop (`border-collie run`) is retained for local use but is no longer the primary path: a Tick fires on pull request closure, on a Worker job completing, on manual dispatch, and on a half-hourly cron backstop, serialised by a concurrency group. This exists because a laptop-bound loop holds the machine for as long as a run takes — closing the lid kills the fleet mid-Attempt, and there is no way to start a run, walk away, and find pull requests waiting the next morning.

Dispatch is fire-and-forget: the Tick triggers a Worker's job and moves on without waiting for it, the same seam `dispatchWorker` already occupied. A Worker's job classifies its own outcome and performs its own tracker write — opening the draft PR, posting the forensic release, or voiding an Infrastructure failure — through the same settling logic the local path already used, reached through a second CLI entrypoint (`border-collie worker`) rather than a new seam. The next Tick reads the result back from GitHub. This removes the failure mode where a Tick awaited every in-flight Worker before acting on any of them: previously, one slow Worker held up every claim, close, or escalation the Tick would otherwise have made that pass. Worker liveness follows the same move: a restarted Orchestrator no longer needs a promise held in its own process memory to know what is still running, because it can list the Worker workflow's runs on GitHub and treat anything not yet `completed` as live. A Worker's own watchdog still kills a stalled session and settles the Attempt as an ordinary failure; the job's own wall-clock ceiling is a backstop set a margin above the watchdog's, so a Worker's job ending with no settling comment means that backstop fired instead — which the next Tick's orphan check reads the same way it reads any other abandoned Claim.

Worker isolation is the job itself, not a git worktree. One job means one checkout with nothing else sharing it, so the worktree, the repository-level git lock that serialises worktree and ref operations, and worktree pruning are all unnecessary on this path — the Worker entrypoint takes an `--in-place` flag that checks out directly into the job's own working directory instead of allocating one. The local path keeps the worktree, because concurrent local Workers still share one checkout.

The Worker runner is the same headless `claude` CLI the local path already used, run inside the job rather than `claude-code-action`. `claude-code-action` was the pending alternative before the credential spike; running raw headless `claude` under the Actions job kept the existing classification pipeline, the fleet heartbeat's arithmetic, and the stall watchdog unchanged, none of which `claude-code-action` was known to expose a seam for.

**This reinforces ADR 0001 rather than contradicting it.** That decision already commits border-collie to a stateless Orchestrator, with GitHub as the only state store and every Tick recomputing the dispatchable set from `gh`. The circuit breaker and Attempt history had already made that move independently, in earlier tickets not scoped to this one — this substrate's own contribution is Worker liveness, read from GitHub's job-run listing instead of a promise held in memory. What changes is not how much state a Tick is allowed to keep, but whether it *can* keep any: a resident process could always cheat that discipline by holding something across polls without it showing, while a Tick that is a fresh Actions job every time has no memory to cheat with — the first substrate that actually forces the stateless design to hold.

## Considered Options

- **Keep the resident run loop as the only path** — rejected as the primary path: it is retained for local use, but it is what makes border-collie laptop-bound, which is the problem this ADR exists to fix.
- **Cloud sessions as the Worker substrate** (a hosted conversational Claude Code session per Ticket, rather than a job running the CLI) — rejected: it forfeits the classification pipeline that turns a session's outcome into a `WorkerOutcome`, and it only reopens if headless `claude` fails on both runners under the credential spike.
- **`claude-code-action` as the Worker runner** — the contingency plan pending the credential spike, not taken: the spike resolved in favour of raw headless `claude`, keeping the Worker's classification, heartbeat, and watchdog machinery unchanged rather than re-scoping it against whatever the action exposes.
