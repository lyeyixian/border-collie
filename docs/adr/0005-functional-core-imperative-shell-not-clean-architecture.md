# Functional core / imperative shell for src (Clean Architecture considered and rejected)

`src` is grouped into four layers named for their relationship to the outside world: `core` (pure functions — types, plan, breaker, render, config, classify), `adapters` (I/O — tracker, worker, pr, config-file), `app` (wires core and adapters together — tick, run, act), and `cli` (delivery — the command application, its composition-root context module, and the entry point). Permitted dependency direction is `core -> core only`, `adapters -> core`, `app -> core, adapters`, `cli -> core, app, adapters`, each restricted by lint so a violation fails in the same session it's introduced rather than surfacing in review. The `cli` layer is allowed to reach `adapters` because its context module is the composition root — it exists so command handlers never import an effect directly.

Clean Architecture (entities / use-cases / interface-adapters / frameworks, with named ports and a composition root) was considered and rejected. The Orchestrator already has dependency inversion: the effects executor declares its collaborators as exported function types and the run loop takes its dependencies as an injected record — ports, expressed as function types rather than interfaces. Adopting Clean Architecture would restate that structure as named interfaces, each with exactly one implementation, plus formal port/adapter ceremony around a codebase that is already inverted. That's ADR 0002's tracker seam again, one level up: a seam is worth naming and formalizing once there's a real second implementation behind it, and until then the informal version costs less to read.

The condition that reverses this: **a second tracker (Linear, Jira, GitLab) or a second Worker runtime.** Either gives a function-type port a genuine second implementation, at which point promoting it to a named interface earns its keep. Neither is planned.
