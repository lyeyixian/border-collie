# Serialise conflict resolution behind the operator's merges, and verify it with the repository's own CI

A Conflict Worker is dispatched only when no open agent pull request is currently mergeable, against exactly one conflicted pull request per Tick — the one whose merge unblocks the most downstream tickets, lowest pull request number breaking ties. Every other conflicted pull request waits, carrying a marker comment that says which one it is queued behind. This exists because PR upkeep previously dispatched a Conflict Worker against *every* conflicted pull request in the same Tick, and each merge the operator then made re-conflicted the ones still open: landing N pull requests cost O(N²/2) Worker sessions where N−1 would have done. Resolving a pull request that is not the next to merge is speculation, and the speculation is invalidated by the very next merge.

The invariant is stated as a property of the world snapshot rather than as a lock, so it survives the stateless Orchestrator of ADR 0001: *dispatch a Conflict Worker only when no open agent pull request is currently mergeable*. That is stronger than "one at a time" and it is the correct rule, because any pending merge invalidates any resolution, not merely the next one. It also survives the draft flip below — a resolved-but-unmerged pull request stays mergeable while it sits as a draft, so it keeps the queue closed until the operator actually merges it. Nothing is held in memory between Ticks; a Tick reads the mergeability of every open agent pull request and derives the answer.

**A resolution is now verified before it can be merged, and the verifier is not the agent.** The Worker's only success test was whether git finished the rebase — a mechanical question that says nothing about whether the resolved code still works, and git will complete a rebase around a resolution that silently dropped one side. On a successful resolution the Orchestrator now converts the pull request to draft after pushing. A draft cannot be merged, so the operator cannot land a resolution they never re-read; the existing draft-to-ready flip restores it once CI is green, and a resolution that breaks CI already trips a Refinement round through machinery that exists. No new configuration is introduced: border-collie stays ignorant of the target repository's toolchain, reading the CI standing it already models rather than running a build itself.

**The Conflict Worker prompt no longer delegates its procedure to a third-party skill.** It invoked `/resolving-merge-conflicts` from an external marketplace, with a prose fallback for when the slash command was unavailable — so the quality of a core behaviour depended on whether a plugin happened to be installed in the Worker's environment, and degraded silently when it was not. The procedure is now inline, versioned and tested with the code, as `refinementWorkerPrompt` already was. Being inline is also what makes the two clauses the contract had been missing expressible: never drop one side to make a conflict disappear, and stop rather than guess when the resolution needs information present in neither side. Abstention needs no new plumbing — a Worker that stops without completing the rebase already reports unresolved, which asks a human, which is the correct outcome.

The evidence behind all of this is in `docs/research/agent-fleet-pr-integration.md`. Three findings carried the decision. Automated conflict resolution tops out near 55–65% correct and has barely improved since GPT-3, so shipping an unverified resolution onto a branch the operator has already approved is the real exposure — not the fan-out. Structural correctness cannot be delegated to a model, which is why the verifier is CI rather than the Worker's own report. And the reassuring finding that generative models "fail loudly" comes from single-shot models whose failure mode is token truncation; an agentic loop with file access and retry has no such failure mode and will iterate until its output merely looks clean, so that safety property should not be assumed here.

**This is a mitigation, not a cure.** Conflicts arise because concurrent tickets touch the same files, and measured against this repository the overlap is architectural rather than incidental: the median commit changes 6 of 32 source files, only 6% touch exactly one, and `worker.ts` appears in 48% of all commits. Preventing conflicts — by constraining which tickets may be dispatched concurrently — is deliberately out of scope here and left as future work.

## Considered Options

- **Resolve every conflicted pull request eagerly, as before** — rejected: it is the O(N²/2) behaviour this ADR exists to remove, and it buys nothing, because a conflicted pull request cannot be merged, so pre-resolving one the operator cannot reach next has no wall-clock upside.
- **Stop resolving conflicts automatically and hand every conflicted pull request to a human** — rejected: measured agent-PR conflict rates put Claude Code near 26%, so this would route a quarter of all pull requests through the operator, which is the bottleneck the product exists to remove. The human baseline is also weaker than it looks — conflict code that required manual intervention is 26× more bug-prone.
- **Discard the conflicted branch and re-dispatch the ticket against the current base** (Google's regenerate-rather-than-merge posture for large-scale changes) — rejected on cost: regeneration is a full Attempt where a resolution is a partial one, so it is strictly more expensive per unit than serialising, and it discards completed review and any Refinement rounds. Recorded because it is the only strategy in the survey that escapes the accuracy ceiling entirely, and border-collie is one of the few systems that *has* a generator.
- **Adopt GitHub's native stacked pull requests** (public preview since 2026-07-30) — rejected: our pull requests are siblings branched off the base, not a stack, so a stack would require either serialising dispatch, which forfeits the fleet, or restacking retroactively, whose rebase *is* the conflict session being avoided. Retroactive stacking reaches the same N−1 floor as serialising, for a stack lifecycle and a preview-stage API.
- **Debounce — suppress Conflict Workers for some number of Ticks after a merge lands** — rejected: merges are already gated on resolutions, since a conflicted pull request cannot be merged, so a debounce window adds latency without removing a single speculative session.
- **A `verify_command` configuration field, run in the worktree before pushing** — not taken: it would catch a broken resolution before the branch moves, but it breaks the property that `ResolvedConfig` carries only fleet knobs and nothing about the target repository's toolchain, and it relies on the same test suite CI runs. Reopens if the CI-less case below proves painful.
- **Let the Worker verify and report its own success** — rejected on direct evidence: a calibrated LLM judge accepted four of the five resolutions that failed a deterministic structural check.
- **Ship our own conflict skill, scaffolded into target repositories by `init`** — rejected: it trades one install dependency for another and adds scaffold drift, where a repository scaffolded months ago carries a stale copy. The procedure is invoked from exactly one place by one caller, so the sharing that justifies a skill does not apply.
- **A timeout escape hatch, resolving the next conflict anyway once the queue has been idle** — not taken: a stalled queue means a ready-to-merge pull request is sitting in front of it, which is a signal for the operator to act on rather than one the Orchestrator should route around by spending tokens.
- **An operator override label pinning the front-runner** — not taken: a second lever for a problem not yet observed. The default ordering is reversible and cheap to change.
- **Adopt Orca, Goose, or Flue as a substrate** — rejected: none of them models this problem. Goose closed both its worktree and its git-coordination issues as declined and reports a hardcoded success status a poll loop cannot trust; Flue has no model of version control at all; Orca overlaps border-collie's core but is a five-month-old Electron desktop application whose own conflict handling is still one pull request at a time.

## Known Limitations

- **A conflicted pull request waits behind every mergeable sibling, not merely the front-runner.** The wait is bounded — Scope is a fixed ticket set, and a queued pull request occupies the `max_open_prs` headroom that would otherwise dispatch more work — but it can be long. The timeout and the override label above are the escape hatches if it bites.
- **In a repository with no CI, the verification is absent.** A CI standing of `none` flips a draft straight back to ready, so the resolution ships unchecked, exactly as it did before. No worse than the previous behaviour, but the teeth are missing where they would matter most, and this is the strongest argument for revisiting `verify_command`.
- **CI is a weak oracle for the failure mode this guards against.** Auto-generated unit tests detected nine of 28 semantic conflicts in the one study that measured it. A resolution that silently drops one side and still passes the suite will reach the operator; what the draft flip guarantees is that they must look at it, not that the machine caught it.
