# A hosted daemon as the execution substrate, not GitHub Actions

*Supersedes ADR 0006.*

The Orchestrator and every session it dispatches move off GitHub Actions onto a long-running daemon on a Linux host the operator owns. The daemon herds every repository the GitHub App is installed on from one process, walking the fleet on an interval and running one Tick per repository, serialised per repository by its own lock in place of the Actions concurrency group. A target repository keeps no workflow files at all: `init` stops writing them, and `scripts/sync-workflow-version.mjs`, the per-repository version-pin commit it existed to automate, and the release-ordering hazard that commit created all go away with it.

**What ADR 0006 got right survives the move, because the daemon answers the same complaint by a different route.** A laptop-bound loop dies when the lid closes — that was ADR 0006's founding complaint, and it is still true; GitHub Actions was one way to stop being laptop-bound, a hosted daemon is another. Dispatch is still fire-and-forget: the Tick starts a session and moves on without waiting for it, the same seam `dispatchWorker` has always occupied. A session still classifies its own outcome and performs its own tracker write — opening the draft PR, posting the forensic release, or voiding an Infrastructure failure — through the same settling logic, reached through the same `border-collie worker` entrypoint. And isolation is still one dedicated environment per session, never a shared one: ADR 0006 got that from the Actions job itself; the daemon gets it from a container.

**What changed is the substrate underneath those same shapes, not the shapes.** Every session — a Worker Attempt, a Conflict Worker, a Refinement round — now runs in its own **session container**: a fresh container built from the target repository's declared Dockerfile, layered with Node, Claude Code, `gh` and border-collie so the repository's own Dockerfile never pins a border-collie version and the problem this ADR exists to solve is never re-inherited one layer down. A repository with no declared Dockerfile still runs; `declare` reports the gap the same way it reports an empty verify contract, rather than refusing — the same declare-not-author posture the verify contract already keeps, owed to `WORKFLOW.md` by a repository-contract decision record this reconciliation did not settle. Conflict Workers and Refinement rounds move into containers too, which they did not get from ADR 0006: on the Actions path they ran synchronously inside the Tick's own job, so a slow one held up every other action that Tick would otherwise have taken for that repository. In a daemon herding many repositories from one process, that stops being a per-repository annoyance and becomes a fleet-wide one — a stalled resolution in one repository must never freeze the Tick for every other repository the daemon herds — so both now launch detached, exactly as a Worker does.

**Liveness moves from a job-run listing to a container label.** ADR 0006 read Worker liveness by listing the Worker workflow's runs on GitHub and treating anything not `completed` as live — a query against Actions' own bookkeeping. A container carries no such registry, so the daemon labels each one with its repository, Ticket and Attempt at launch, and a Tick derives liveness by listing containers and reading those labels back. The property ADR 0006 cared about is preserved exactly: a restarted process reaches the same verdict a long-running one would, because nothing about the answer lives in the process that asks. It is also what makes a daemon restart free — every container runs detached, a session settles its own Attempt against the tracker exactly as it always has, so a daemon that comes back after a crash or an upgrade re-adopts whatever is still running by label and loses no work in flight. That is the whole point of moving off Actions: upgrading the fleet becomes upgrading one process, and re-adoption is what makes that upgrade cost nothing.

**The credential model tightens rather than loosens.** An Actions job's token, minted by `claude-code-action` or the workflow's own `GITHUB_TOKEN`, covers the whole installation for the job's lifetime. The daemon holds the GitHub App's private key itself and mints a short-lived installation token per Attempt, scoped with `repository_ids` to that Attempt's one repository — a session running for one repository cannot reach another, and a leaked token is bounded by the hour it expires in rather than by the installation's full reach. The private key itself never enters a session container: it is minted where the daemon runs, handed to the session as a token, and the code a Worker runs cannot mint a token for itself.

**The set of state the daemon may hold across Ticks is exactly what `run` already held, and the list is closed.** ADR 0001 committed the Orchestrator to being stateless — GitHub is the only state store, every Tick recomputes the dispatchable set from `gh` — and ADR 0006 already observed that a resident process could always cheat that discipline by holding something across polls without it showing, while a fresh Actions job per Tick had no memory to cheat with. The daemon gives that discipline its memory back, so the list has to be named rather than assumed:

- **The circuit breaker**, one per repository — trip count and cooldown timer, held in process memory exactly as `run.ts` already holds it today for the single-repository resident loop. Losing it costs at most one voided Attempt before it re-trips, because a Tick also derives a breaker from the tracker's own void markers independently.

Nothing else is held. Fleet membership is not a list the daemon keeps — it is `GET /installation/repositories`, read fresh every poll, so installing the App is what adds a repository and uninstalling is what removes one. Worker liveness is not held either — it is read from container labels every Tick, as above. A per-repository lock exists to serialise that repository's Ticks, but it carries no information from one Tick to the next and so is not state in this sense — it is closer to the Actions concurrency group it replaces than to anything on this list. Fleet policy (`maxOpenPrs`, the working-hours window, per-repository overrides) is operator-supplied configuration read from one file on the daemon host, not derived from the tracker, so it is not subject to this rule at all; `border-collie.json` is retired, since loop policy on a file a repository can edit was always the wrong place for it. A future change that adds to the state above is a decision somebody makes on purpose, against this list, not a drift nobody notices.

**Loop-control tracker state is the Orchestrator's to write, never a Worker's.** The Claim label (`border-collie:claimed`) and its markers (`CLAIM_MARKER`, the release marker, `VOID_MARKER`), the Attempt markers (`attemptMarker`/`parseAttemptMarker`), the `border-collie:operator-steered` label, and the Refinement markers (`REFINEMENT_ROUND_MARKER`, `REFINEMENT_GIVE_UP_MARKER`) are written only by the Orchestrator code a session runs to settle itself — `border-collie worker`'s own settling path — never by the agent session a Ticket's Worker runs to do the Ticket's actual work. A Worker's agent session may read the tracker freely; it must never write a Claim, an Attempt marker, a void, the operator-steered label, or a Refinement marker itself. This is not new to the daemon — it was already true on every prior substrate — but it was never written down, and a Worker migrated this repository's own labels mid-flight once, from inside its agent session rather than through the settling path, and three Tickets got duplicate Workers dispatched against them before anyone noticed the claim state it left behind was fiction. The daemon raises the stakes of getting this wrong: one daemon herding many repositories means one mis-scoped write reaches every repository the token it ran under could touch, not just the one the job happened to check out. The rule is named here because it is a property of who may write loop-control state, independent of which substrate is running the session, and because settling this reconciliation was the moment to write it down rather than rediscovering it after the next incident.

## Considered Options

- **Keep GitHub Actions as the substrate** — rejected: the GitHub App deliberately excludes the Workflows permission so that a Worker can never rewrite the workflow file that runs it, which means every change to the loop that touches a workflow file is work the fleet is structurally incapable of doing (issue #153 is the proof), and every release is a version-pin commit repeated in every onboarded repository.
- **Webhooks instead of a poll** — rejected: a webhook needs a public hostname, inbound exposure and a delivery secret the daemon would then have to protect; a poll needs none of those, and the daemon reacting to a session container exiting closes most of the latency gap a webhook would have bought.
- **A shared per-repository checkout on the daemon, with worktrees the way the local path already works** — rejected: it forfeits the isolation a session container buys. A Worker's clean environment on the Actions path came from the job being its own checkout with nothing else sharing it; a worktree shared with sibling sessions on the daemon reopens the repository-level git lock the Actions path removed, for no isolation gain over a container the daemon can build once and reuse.
- **A single long-lived installation token held by the daemon, rather than one minted per Attempt** — rejected: it covers the whole installation for as long as the daemon runs, which is strictly broader than the per-repository, hour-bounded token an Attempt gets today. Minting per Attempt costs one API call and buys back both the scope and the lifetime.
- **Let the daemon keep a cached list of installed repositories, refreshed on some interval** — rejected: it is a second registry that can drift from the App's own installation list, which is exactly the kind of state ADR 0001 already rejected keeping — a fleet membership question GitHub can answer authoritatively costs nothing to ask fresh every poll.

## Known Limitations

- **The daemon is a new single point of failure the fleet did not have on the Actions path.** Actions gave every job its own fresh runner; a daemon that crashes mid-poll stops herding every repository at once until it restarts. Detached session containers and label-based re-adoption bound the cost of a crash to the polling gap, not to lost work, but the process itself is now something the operator has to keep running, where Actions kept it running for free.
- **The adoption floor rises.** Running border-collie now means running a server — a host, a systemd unit, disk for transcripts and container images — rather than pointing GitHub Actions at two workflow files. The roadmap's audience constraint says the operator is the only user who matters for v2, so this is accepted rather than worked around, and is stated plainly in the README rather than discovered.
